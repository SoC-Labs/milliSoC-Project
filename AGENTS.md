# milliSoC — Project Context and Engineering Agent Instructions

## 1. Project Overview

milliSoC is a reusable, configurable System-on-Chip (SoC) reference platform for real-time Edge AI, developed as part of SoC Labs at the University of Southampton.

The objective is to provide a practical, modular hardware platform that allows researchers, students, and small engineering teams to integrate, evaluate, and eventually tape out novel AI accelerators and application-specific IP without having to develop an entire SoC infrastructure from scratch.

The platform should be suitable for both research experimentation and real-world embedded applications that require a combination of deterministic real-time control, programmable processing, and hardware-accelerated AI.

The development strategy is to:
1. Establish a working, synthesizable baseline SoC.
2. Develop and validate the design through simulation and FPGA prototyping.
3. Integrate and evaluate configurable AI accelerator IP.
4. Mature the design toward ASIC implementation and silicon tapeout.
5. Produce a reusable reference design, documentation, firmware infrastructure, and integration methodology that external users can adapt to their own research.

This is an evolving platform, not a fixed commercial product. Modularity, understandable architecture, reproducibility, and ease of integration are important design objectives.

## 2. Target Architecture

The baseline milliSoC architecture is a heterogeneous multiprocessor system containing three primary compute elements:

- **Arm Cortex-R5:** The master processor responsible for system control, real-time decision-making, coordination, and supervision of the other processing elements.
- **Arm Cortex-M85:** A programmable processing core intended for application-level processing, data handling, signal processing, and AI-related workloads.
- **Configurable NPU / AI accelerator:** A hardware acceleration subsystem for neural-network inference and other application-specific computation.

The Arm Ethos-U85 is a planned demonstrator implementation of the NPU subsystem. However, the platform must not be architecturally dependent on the Ethos-U85. Researchers should be able to replace it with their own accelerator IP, including custom research accelerators.

The Ethos-U85 demonstrator and the ability to integrate independent research accelerators are equally important aspects of the platform.

Keep these architectural roles distinct:
- The R5 is the master and system coordinator.
- The M85 provides programmable application and data-processing capability.
- The NPU is a configurable acceleration resource, not a mandatory fixed implementation.

The architecture should support heterogeneous parallel execution and explicit coordination between processing elements. Interprocessor communication, synchronization, shared-memory coordination, and interrupt handling are fundamental platform requirements.

## 3. Memory Architecture

The intended memory architecture includes:

- **Boot ROM:** Provides the initial execution and boot infrastructure.
- **QSPI flash interface:** Provides access to external non-volatile storage containing firmware and other images.
- **Private tightly coupled memories (TCMs):** The R5 and M85 each have their own private SRAM resources for low-latency, predictable execution.
- **Shared memory:** Provides a common memory space for communication, data exchange, coordination, and shared buffers between processing elements and accelerators.
- **Peripheral and system-control registers:** Provide access to interrupt controllers, timers, UARTs, accelerator controls, and other platform functions.

The boot path should follow the ROM-to-QSPI-to-SRAM/TCM model, adapted to the actual implemented memory map and boot configuration.

Private memory and shared memory must be treated as distinct architectural resources. Do not assume that all processors have identical memory visibility, address maps, access permissions, or cacheability.

When proposing memory changes, explicitly consider:
- Address-map consistency across RTL, firmware, linker/scatter files, and testbenches.
- Arbitration and access permissions.
- Memory initialization and reset behavior.
- Synchronization and cache coherency where applicable.
- Deterministic access requirements for real-time execution.
- How accelerator DMA or bus-master accesses interact with processor-local and shared memory.

Do not assume cache coherency exists unless it is explicitly implemented and verified.

## 4. Boot and Processor Coordination

The R5 is the system master and controls system initialization and the startup of the other processing elements.

The R5-first boot strategy is implemented and working (verified in VCS simulation, `hello` test):
1. On reset the Cortex-R5 starts in boot ROM, which contains the second-stage bootloader image (generated by `make bootrom` from `millisoc_sdk/bootloader/`).
2. The bootloader initializes UART, caches, QSPI flash, and the PL192 VIC (vectored interrupts enabled via the SCTLR VE bit).
3. It reads the 4-word image preamble at `FLASH_BASE` — M-class offset and size, then R-class offset and size, sizes in 32-bit words, offsets relative to flash address 0 — as produced by `millisoc_sdk/tools/concat_hex.py`.
4. Using the DMA350 (completion interrupt serviced through the VIC), it copies the M-class image to `0x00000000` (M85 ITCM) and the R-class image to `0x80000000` (R5 ATCM).
5. It releases the M85 by clearing `sysctrl->cpu_mx_wait` (the `cpu_mx_wait` register in `millisoc_sys_ctrl` drives the M85 `CPUWAIT` input), then branches into its own preloaded image.
6. Both cores run their applications. Explicit interprocessor communication, shared-memory coordination, and supervised operation between the cores are not yet implemented — do not assume they exist.

Preserve the ability to control or reset the M85 independently where the implemented architecture permits it.

The precise boot sequence must follow the actual RTL, processor integration configuration, and available control signals. Do not assume a reset, CPUWAIT, or image-loading mechanism exists without checking the RTL and firmware — the mechanisms described above are the ones actually implemented.

## 5. Current Implementation and Development Status

The project is under active development; the baseline two-core boot path is working in RTL simulation.

Current status:
- Cortex-M85 integration: baseline complete; firmware executes from ITCM after boot release.
- Cortex-R5 integration as system master: working; the R5 boots from ROM, runs the bootloader, services interrupts, and executes its applications.
- Boot: two-stage R5-first boot works end to end (flash preamble → DMA preload of both TCMs → M85 released from CPUWAIT). The `hello` test passes with both cores printing their banner (see `simulate/sim/hello/logs/`).
- ROM, SRAM, and QSPI flash controller: integrated and proven along the boot path.
- Bus infrastructure and memory mapping: in place; UART and timer peripherals working in simulation.
- Interrupt controller: PL192 VIC integrated and driven by firmware (`millisoc_sdk/libs/Drivers/Source/vic.c`); the bootloader receives DMA channel 0 completion interrupts through it.
- Configurable NPU integration: preparation only.

The platform has moved away from the GIC-400 in favour of the simpler PL192 VIC. The interrupt infrastructure should use the PL192 VIC driver, register definitions, and interrupt handling model consistent with the PL192. Ensure firmware, RTL, and configuration all agree on the VIC interface, address map, and interrupt routing.

`docs/r5_boot_isb_sensitivity_analysis.md` documents an earlier boot failure (ISB-ordering sensitivity in the R5 bring-up) that predates the current working boot; treat it as background analysis, not current status.

The implementation status will evolve. Always inspect the current repository and latest logs before assuming that a historical issue is still present or that a previously proposed change has been implemented.

## 6. Software and Toolchain

Both the M-class and R-class firmware build with Arm Development Studio 6 (`armclang`, `armlink`, `fromelf`) via the SDK's `all_ds6` target. Applications are split into `<name>_M.c` (Cortex-M85) and `<name>_R.c` (Cortex-R5); the two hex images are combined into a single flash image — 4-word little-endian preamble followed by both payloads — by `millisoc_sdk/tools/concat_hex.py`. The bootloader is also `ds6`-built (for the R5).

The software infrastructure should support the necessary processor startup, initialization, exception handling, memory layout, and peripheral drivers. CMSIS-compatible definitions and headers, such as `core_cm85.h`, are relevant where appropriate to the actual processor integration.

Firmware artifacts may include:
- Reset and startup code.
- Vector tables and exception handlers.
- Linker or scatter-loading files.
- Memory and peripheral definitions.
- Boot firmware.
- Drivers for UART, timers, interrupt controllers, and other peripherals.
- Interprocessor communication and synchronization code.
- Accelerator initialization and test firmware.
- Bare-metal tests and diagnostic applications.

Keep software assumptions aligned with the RTL. A correct CMSIS definition or register access does not establish that the corresponding peripheral is correctly mapped, clocked, reset, or connected in the hardware.

Use the compiler, simulator, build system, and EDA tools already configured in the repository unless there is a concrete reason to propose a change.

## 7. Reusability and Configurability

A core design principle is that milliSoC must be reusable by people who did not create the original implementation.

The architecture should therefore make it reasonably straightforward to:
- Replace or modify the NPU.
- Integrate custom research accelerators.
- Add or remove peripherals.
- Adjust memory sizes and address mappings.
- Change accelerator interfaces and control registers.
- Develop custom firmware and applications.
- Adapt the platform to different FPGA and ASIC targets.

Where practical, separate stable platform interfaces from implementation-specific IP.

Use clear interface contracts for accelerator integration, including control and status registers, interrupt behavior, memory access, reset, clocking, data movement, and error reporting.

Do not over-generalize the initial implementation. Prefer a simple, working baseline with well-defined extension points over an unnecessarily complicated framework.

## 8. Engineering Priorities

Prioritize the following, in order appropriate to the immediate task:

1. **Functional correctness:** The design must behave as intended in simulation and hardware.
2. **Debuggability:** Failures should be observable through useful logs, assertions, status registers, waveforms, and reproducible tests.
3. **Integration correctness:** Processor interfaces, bus protocols, memory maps, interrupts, reset, clocking, and firmware must agree.
4. **Reusability:** New IP should be integrable without invasive changes to unrelated platform components.
5. **Verification:** Changes should have a clear validation strategy, with regression tests where practical.
6. **Synthesizability and implementation readiness:** RTL must be suitable for the intended FPGA and eventual ASIC flow.
7. **Maintainability:** Prefer understandable code, explicit configuration, and documented design decisions.

Do not optimize prematurely for maximum performance, minimum area, or the most elaborate architecture before the basic platform is working.

Where real-time determinism is required, explicitly distinguish deterministic local execution from accesses that depend on shared buses, shared memory, or other competing masters.

## 9. How You Should Work as the Engineering Agent

Act as an experienced SoC integration, RTL, firmware, and verification engineer.

Before making significant changes:

1. Inspect the relevant repository files and directory structure.
2. Identify the existing implementation, interfaces, configuration parameters, and coding conventions.
3. Trace the affected behavior across RTL, firmware, memory maps, build scripts, and testbenches as appropriate.
4. Establish the likely failure mechanism or implementation requirement from evidence.
5. Form a minimal, testable implementation plan.

When debugging:
- Identify the exact point at which observed behavior diverges from expected behavior.
- Use simulation traces, disassembly, register values, bus waveforms, assertions, and logs where available.
- Distinguish observed facts from hypotheses.
- Check whether transactions complete and whether reset, clocking, security, privilege, and address decoding are correct.
- Avoid treating a processor hang as proof of a CPU bug; investigate the surrounding system and interconnect.
- Propose targeted experiments that discriminate between competing explanations.

When editing:
- Make focused changes rather than broad rewrites.
- Preserve existing functionality unless a change is necessary.
- Follow the repository's established coding and formatting conventions.
- Keep generated files, vendor IP, and hand-maintained source files distinct.
- Do not invent module names, parameters, register offsets, signal behavior, or tool commands. Inspect the source or authoritative documentation.
- Avoid introducing dependencies or tools that are not already available without explaining why they are needed.

After making changes:
1. Run the narrowest relevant test first.
2. Run broader regressions where feasible.
3. Inspect compiler and simulator output for warnings, errors, and unexpected behavior.
4. Report precisely which checks passed, failed, or could not be run.
5. Identify remaining assumptions, limitations, and follow-up work.

Never claim a design has been verified, synthesized, or tested unless the corresponding operation was actually performed and its result inspected.

## 10. Technical Decision-Making

When multiple approaches are possible, compare them against milliSoC's actual goals:
- Simplicity for small engineering teams.
- Low integration overhead.
- Clear interfaces and modularity.
- Reliable real-time behavior.
- Compatibility with FPGA prototyping and eventual ASIC implementation.
- Practical integration of third-party and research IP.
- Reasonable verification effort.

Prefer established, well-understood protocols and IP integration patterns when they meet the requirements.

Do not introduce architectural complexity merely because it is theoretically more scalable. Conversely, do not hard-code a design choice that unnecessarily prevents future accelerator substitution or platform reuse.

If an architectural decision has not yet been made, present the trade-offs and recommend a practical default. If a decision has already been established in this document or is clearly reflected in the implementation, do not silently overturn it.

When information is missing, inspect the repository first. Ask for clarification only when the uncertainty materially affects correctness or when the necessary information cannot reasonably be recovered from the available files.

## 11. Expected Deliverables

Depending on the task, produce concrete engineering outputs such as:
- RTL modifications.
- Firmware and driver changes.
- Memory-map and register documentation.
- Testbenches and directed tests.
- Assertions and verification utilities.
- Build and simulation scripts.
- Debugging reports with evidence and root-cause analysis.
- Architecture notes and integration guides.
- Reproducible instructions for running tests and validating changes.

For each substantive task, finish with a concise report containing:
- What changed.
- Why the change was needed.
- Which files were modified.
- Which tests or commands were executed and their actual results.
- Any unresolved risks or next steps.

## 12. Long-Term Vision

The long-term goal is a practical, reusable real-time Edge AI SoC platform that bridges academic accelerator research and real hardware implementation.

A user should be able to take milliSoC, understand its architecture, integrate a novel accelerator, develop the necessary firmware, validate the complete system, and progress toward FPGA demonstration and ASIC tapeout without having to reinvent the surrounding SoC infrastructure.

Optimize engineering decisions for that outcome: a working, understandable, verifiable, and extensible platform rather than a one-off demonstration.

When in doubt, prioritize a correct and well-tested implementation over a speculative architectural improvement.

# Repository Guide (verified against this checkout)

## What this is

RTL simulation project for the milliSoC SoC platform (Arm Cortex-R5 system master +
Arm Cortex-M85). Almost everything is a git submodule: `millisoc_tech` (RTL + IP),
`millisoc_sdk` (bare-metal software), `soctools_flow` (build scripts),
`rtl_primitives_tech`, `generic_lib_tech`, `asic_library_tech`, `asic_flow`.
The root repo itself holds the makefile glue, config, flists, testbench,
`README.md`, `AGENTS.md`, and `docs/`. `README.md` is a maintained project
overview (architecture, getting started, flash image format, current status) —
keep it in sync with reality. `docs/` currently holds
`r5_boot_isb_sensitivity_analysis.md`, a historical analysis of an earlier boot
failure (background only — the boot flow now works).

Under `millisoc_sdk/` (submodule), trust the Makefiles over any prose —
**`millisoc_sdk/AGENTS.md` is known to be out of date** (claims DS-5 default,
no in-tree CMSIS, artifacts in app dirs — all wrong now). Verified SDK facts:

- Default and only working toolchain is `ds6` (armclang, `armlink`/`fromelf`).
  Root `makefile` exports `TOOL_CHAIN=ds5`, but the SDK Makefile hard-assigns
  `ds6`, so apps actually build with armclang. The `gcc` flow references a
  missing `common/` tree and linker script (broken); `keil` is a placeholder.
- `CPU_TYPE` (from root config, currently `CM85`) selects device dir/startup:
  M85 uses `libs/Device/M85/exectb_mcu`, startup `boot_exectb_mcu`.
- Apps live in `millisoc_sdk/apps/<TESTNAME>` (currently `hello`,
  `reset_demo`); artifacts go to `millisoc_sdk/build/<TESTNAME>/`, which is
  where the root `testcode` flow copies `image.hex` from. `hello` is split
  into `hello_M.c`/`hello_R.c`; `reset_demo` is still single-file and has not
  been converted, so `all_ds6` fails for it (no `reset_demo_R.c` — verified).
- `all_ds6` builds `<TESTNAME>_M.hex` and `<TESTNAME>_R.hex` (fromelf
  `--vhx --8x1`: one hex byte per line, no address records) and combines them
  into `<TESTNAME>.hex` with `millisoc_sdk/tools/concat_hex.py`: a little-endian
  4-word preamble (M offset, M size in 32-bit words, R offset, R size; offsets
  from the start of the flash image, so M always starts at `0x10`) followed by
  both payloads. Root `testcode` copies that combined file to `image.hex`; the
  testbench preloads it into the flash model and the bootloader consumes it.
- CMSIS headers are in-tree at `millisoc_sdk/libs/CMSIS/include`
  (`core_cm85.h` etc.).
- The bootloader builds for **Cortex-R5** (`bootloader/`, scatter
  `scatter/R5/armclang_bootrom.scat`); its hex becomes the generated bootrom,
  which the R5 executes at reset. The two-stage boot works end to end: the
  bootloader preloads both TCMs from the flash preamble and releases the M85
  from CPUWAIT.
- Scatter files — `scatter/M85/armclang.scat` (M-class apps),
  `scatter/R5/armclang.scat` (R-class apps),
  `scatter/R5/armclang_bootrom.scat` (bootloader) — are referenced by
  **hard-coded absolute paths** in `millisoc_sdk/Makefile` and
  `bootloader/makefile` — moving the tree breaks linking until those are
  updated.

## Environment setup (required before any make)

- Everything runs through `source set_env.sh` (source it, don't execute). It
  locates the project by walking up to the `.slprojroot` marker and exports
  `SOCLABS_PROJECT_DIR` plus all `SOCLABS_*_DIR` vars (via
  `env/dependency_env.sh`) and prepends flow tool dirs to `PATH`.
- Requires `ARM_IP_LIBRARY_PATH` pointing at a licensed Arm IP library
  (Cortex-M85 AT640, Cortex-R5 AT575, Corstone-101 BP210 are referenced).
  None of that IP is in the repo; builds fail without it.
- First-time init is driven by the `.socinit` marker. Submodule
  branch-checkout (`subrepo_checkout.py`) is opt-in only:
  `SOCLABS_SETUP_SUBMODULES=1 source set_env.sh`, or `source set_env.sh -f`.
  **`-f` force-reinitialises and can revert submodule working trees** — never
  run it (or the submodule checkout) on a tree with uncommitted work in a
  submodule.

## Configuration

- `millisoc.config` selects the CPU config (`CPU_TYPE=CM85`, `R_CPU_TYPE=CR5`)
  and the Arm IP logical dirs. Examples in `millisoc.config_examples/`.
  `CPU_TYPE` drives which `millisoc_tech/flist/IP/Cortex*.flist` files get
  included and which Tarmac DPI libraries are linked into simulation.

## Build/sim commands (root makefile)

All from the project root, after sourcing `set_env.sh`:

- `make compile SIMULATOR=vcs` — compile RTL. Simulator-specific targets are
  `compile_vcs` / `compile_mti` / `compile_xm`. **You must pass
  `SIMULATOR=vcs|mti|xm`** (or export it): the top-level `compile`/`run`/`sim`
  targets expand to `compile_$(SIMULATOR)` etc., and the exported `SIM` var is
  NOT the dispatch variable — with no `SIMULATOR`, make fails with "no rule to
  make target `compile_`".
- `make run TESTNAME=hello SIMULATOR=vcs` — batch sim (per-test dir
  `simulate/sim/<TESTNAME>/`, log in `logs/run_<TESTNAME>.log`). `make sim ...`
  is the GUI variant.
- `make testcode TESTNAME=<app>` — builds the SDK app via `all_ds6` (M and R
  images plus the combined flash image) and copies
  `build/<TESTNAME>/<TESTNAME>.hex` to `simulate/sim/<TESTNAME>/image.hex`.
  `TESTNAME` must match a directory in `millisoc_sdk/apps/` (default `hello`).
- `make bootrom` — generates the bootrom from the bootloader hex (see below).
- `make gen_defs` — regenerates `top/logical/gen_defines.v` (gitignored,
  auto-run as part of compile).
- `make run_cocotb MODULE=<module> TESTNAME=<tc> SIMULATOR=vcs` — cocotb flow.
  Note: it references `verif/cocotb/` which **does not exist in this repo**
  (cocotb lives in submodules, e.g. `millisoc_tech/logical/ahb_qspi`); the
  root-level cocotb target will fail until that dir is added.

Typical first run: `make compile SIMULATOR=vcs` then
`make run TESTNAME=hello SIMULATOR=vcs`. On success,
`simulate/sim/hello/logs/run_hello.log` shows the R5 bootloader banner
(`Bootloader starting...`, `Flash started...`, `Preload ITCM...`,
`Start main program`), then `Hello SoCLabs MilliSoC` from both the R5 and M85
UARTs, then `Test Ended` (the M85 calls `UartEndSimulation`).

## Flows that are stubs

`flows/lint.mk`, `flows/regression.mk`, `flows/fpga.mk`, `flows/asic.mk` are
**empty files**. Only `flows/software.mk` and `flows/simulate.mk` contain real
targets. Don't go looking for lint/fpga/asic make targets at the root.

## Generated files (gitignored — never hand-edit or commit)

- `top/logical/gen_defines.v` — from `soctools_flow/bin/defines_compile.py`
- `system/src/bootrom/verilog/bootrom.sv` (+ `bintxt/bootrom.bintxt`) —
  `make bootrom` builds the bootloader in `millisoc_sdk`, then runs
  `millisoc_sdk/bootloader/bootrom_gen.py` on its hex. The `.sv` is in the
  sim flist (`flist/top_BEHAV.flist`), so compile needs bootrom generated
  first (compile targets depend on it automatically).
- `simulate/` — all sim build (`simulate/sim/build`) and per-test run dirs

## Repo layout (the parts that matter)

- `verif/testbench/millisoc_tb.sv` — simulation testbench top (module
  `millisoc_tb`); `verif/control/`, `verif/trace/` support it
- `verif/monitors/axi3_logger.sv`, `axi4_logger.sv` — AXI bus activity
  loggers instantiated in the TB (one instance per DUT AXI port, one
  `axi3_<name>.log`/`axi4_<name>.log` per port in the sim run dir). Inputs are
  tapped by hierarchical reference to `u_millisoc.u_millisoc_system.<if>`; see
  the "AXI port monitors" section of the TB. Handshake-only logging, so a hung
  address line with no matching response line pinpoints a stuck access, and a
  `STALL` line marks a `VALID&&!READY` channel
- `flist/top_BEHAV.flist` — top-level sim filelist: milliSoC RTL from
  `millisoc_tech` + local TB + generated `bootrom.sv`
- `flist/millisoc_tb.flist` — TB-only filelist (pulls a Corstone-101
  `cmsdk_uart_capture.v` from `ARM_IP_LIBRARY_PATH`)
- `top/logical/` — generated defines; `system/src/bootrom/` — generated bootrom
- `env/dependency_env.sh` — the authoritative map of `SOCLABS_*_DIR` env vars;
  also references optional dirs not present here (`secworks-aes`,
  `accelerator_wrapper_tech`) — absent ones are only needed if you use those
  features

## Gotchas

- `flows/simulate.mk` `run_mti`/`sim_mti` reference `$(TB_TOP)`, which is never
  defined anywhere in this repo — the Questa (mti) run flow is broken as-is;
  VCS flow works. (`run_mti` also builds code itself; `run_vcs` assumes you
  already ran `compile_vcs`.)
- `set_env.sh` unconditionally prepends the Cortex-M7 Tarmac path to `PATH`
  even though the config selects CM85 — harmless, but don't assume it means
  M7 is in use.
- The `testcode` recipe busy-waits (`sleep 5` loops) for hex files instead of
  failing fast; if a build silently fails, make can hang rather than error.
- VCS sim links Arm Tarmac DPI shared libraries from `ARM_IP_LIBRARY_PATH`
  (version-pinned paths in `millisoc.config`); if the library version changes,
  update `millisoc.config` and `set_env.sh`, don't patch the makefile.
